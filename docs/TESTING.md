# Testing

Four layers, from fastest to slowest. Everything under `app/src/test` runs on the JVM; everything under
`app/src/androidTest` needs a device or emulator.

| Suite | Where | Runs on | Command |
|---|---|---|---|
| JVM unit tests (parsers, validators, use cases, ViewModels, Room mappers) | `app/src/test/java/.../{domain,data,feature,core}` | JVM, JUnit 5 + Turbine + MockK | `./gradlew testDebugUnitTest` |
| Architecture tests (source scanning) | `app/src/test/java/.../architecture` | JVM, JUnit 5 | same command |
| Compose UI tests (stateless screens, light and dark) | `app/src/androidTest/java/.../ui` | device / emulator | `./gradlew connectedDebugAndroidTest` |
| Hilt end-to-end flows | `app/src/androidTest/java/.../e2e` | device / emulator | same command |
| Room DAO and migration tests | `app/src/androidTest/java/.../data/db` | device / emulator | same command |

## 1. JVM unit tests

```
./gradlew testDebugUnitTest                       # everything
./gradlew testDebugUnitTest --tests "*ResultViewModelTest"
./gradlew testDebugUnitTest --tests "*architecture*"
```

Reports: `app/build/reports/tests/testDebugUnitTest/index.html`.

Fakes for ViewModel tests live in `app/src/test/java/.../domain/testing` (`FakeHistoryRepository`,
`FakeSettingsRepository`, `Fixtures`); `MainDispatcherExtension` is in `.../testing`.

### Architecture tests

`app/src/test/java/.../architecture` reads the sources, resources and manifest as text, so a rule break fails the
normal unit-test run (no Android needed). The repository root comes from the `repo.root` system property, which
`app/build.gradle.kts` sets for every unit-test task; from an IDE the tests walk up to the first directory that
contains `app/src/main/AndroidManifest.xml`.

| Rule | Test |
|---|---|
| `domain` imports only java, kotlin, kotlinx, ZXing core and other domain packages (no `android.`, `androidx.`, ML Kit, Firebase, `dagger.`, `javax.inject`; no Hilt/Compose annotations); `data` and `designsystem` never import `feature` | `DomainPurityTest` |
| Features do not import each other (they navigate through `core/navigation` routes) | `DomainPurityTest.featuresDoNotImportEachOther` |
| No `TODO` or `FIXME` anywhere in the Kotlin sources | `CodeHygieneTest` |
| No wildcard imports (main, unit tests, instrumented tests) | `CodeHygieneTest` |
| Every `@HiltViewModel` has exactly one non-private `@Inject` constructor | `CodeHygieneTest` |
| No hard-coded user-visible text in `feature/**`: `Text("...")`, `contentDescription = "..."`, `title = "..."`-style arguments, `showSnackbar("...")`. Preview code (everything from the first `@Preview` or `// Previews` section, and `*Previews.kt` files) and `contentDescription = null` are exempt | `StringResourcesTest` |
| Every `R.string.*` / `R.plurals.*` / `@string/*` used exists in `res/values` (or is generated by `resValue`) | `StringResourcesTest` |
| Every default string and plural exists in all seven translations (ar, de, es, fr, hi, in, pt), keeps the same format placeholders, and the folders match `locales_config.xml` | `StringResourcesTest` |
| Manifest: only the launcher activity is exported, components with intent filters say `exported` explicitly, `usesCleartextTraffic="false"`, `allowBackup="false"`, not debuggable | `ManifestSecurityTest` |

`ArchitectureBaseline` lists violations that exist today and are tolerated (currently the two
`result -> create.preview.GeneratedCodePreview` imports). A rule fails on anything not in that list, so debt cannot grow;
fix a listed violation and delete its entry in the same change (stale entries are printed, not failed).

## 2. Instrumented tests

### Setup that makes them work

* `HiltTestRunner` (`androidTest/.../HiltTestRunner.kt`) is the `testInstrumentationRunner`. It is an
  `AndroidJUnitRunner` that swaps the app class for `HiltTestApplication`.
* `HiltTestActivity` (`app/src/debug/.../HiltTestActivity.kt`, declared in `app/src/debug/AndroidManifest.xml`) is an
  empty `@AndroidEntryPoint` activity. It lives in the debug source set because `ActivityScenario` can only start
  activities declared by the app package, not by the test APK. It is never part of release builds.
* `e2e/TestModules.kt` replaces, for Hilt tests only (`@TestInstallIn`): the Room and DataStore repositories with
  the in-memory fakes in `androidTest/.../fakes`, the ad manager and ad content source with no-ops, and the Play
  in-app updater with a no-op.
* Compose tests do not use Hilt: they call the stateless screens with sample state. The ad composables detect the
  missing Hilt component and draw nothing.

### What is covered

* `ui/BottomNavBarTest` selection and callbacks.
* `ui/HistoryScreenTest` row tap, long press, swipe-to-delete, star, tabs, chips, multi-select bar and every empty
  state (scanned, created, favorites, filter, search).
* `ui/ResultScreenWebsiteTest` the website result and the unsafe-link sheet (Go back to safety, Copy link instead, Open
  anyway), using the real `LinkSafetyChecker` to build the state.
* `ui/ResultScreenWifiTest` Wi-Fi result, masked password, connecting, connected, saved suggestion, could-not-connect
  and the location explainer sheet.
* `ui/CreateFormScreenTest` Generate disabled until valid, inline error only after blur, Wi-Fi form rules.
* `ui/GeneratedScreenTest` Generated screen actions and the Colors / Shapes / Extras editor tabs (no Shapes tab for
  barcodes).
* `ui/SettingsScreenTest` every switch row and the theme / language rows.
* `ui/OnboardingTest` Next, Back, Skip, Get started.
* `ui/PermissionRationaleTest` camera (screen and dialog), photos and location rationale buttons.
* `e2e/ScanAndCreateFlowTest` scan to result to history, and create website to generated to History > Created, through
  the real graphs, ViewModels, use cases and screens.
* `e2e/AppNavSmokeTest` the real `AppNav`: first-run onboarding and switching between the four tabs.

Every `ui` test runs twice, in the light and in the dark theme (`ThemedComposeTest`, JUnit4 `Parameterized`).

The camera cannot be automated, so the end-to-end test plays the scanner: it saves a record through
`SaveScanUseCase` (what the scan screen does on a detection) and navigates to `Result(recordId)` in `E2eAppHost`, a copy
of the `AppNav` shell whose Scan destination is a placeholder.

### Conventions

* The app defines no test tags. Match by visible text or content description, read from resources with
  `Res.string(R.string.xxx)` so the tests follow the device language. `SectionLabel` upper-cases its text, so match
  those with `ignoreCase = true`.
* `internal` composables (for example `OnboardingRoute`) are visible to androidTest.
* Prefer the stateless entry points (`ResultScreen`, `HistoryScreen`, `CreateFormScreen`, ...) with a state object
  built in the test; use `E2eAppHost` only when navigation is the point.

### Running

Emulator or device attached (API 24 and 35 are the supported range):

```
./gradlew connectedDebugAndroidTest
./gradlew connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=com.qrcode.scanner.barcodereader.generator.scan.qrcode.createqrcode.ui.HistoryScreenTest
```

Turn the animation scales off on the device first (Developer options, or
`adb shell settings put global window_animation_scale 0` and the same for `transition_animation_scale` and
`animator_duration_scale`).

Gradle Managed Devices are configured in `app/build.gradle.kts` (`testOptions.managedDevices`), so no emulator has to
be started by hand. The task name is `<device><Variant>AndroidTest`:

```
./gradlew pixel2Api24DebugAndroidTest -Pandroid.testoptions.manageddevices.emulator.gpu=swiftshader_indirect
./gradlew pixel6Api35DebugAndroidTest -Pandroid.testoptions.manageddevices.emulator.gpu=swiftshader_indirect
```

```kotlin
testOptions {
    managedDevices {
        localDevices {
            create("pixel2Api24") { device = "Pixel 2"; apiLevel = 24; systemImageSource = "aosp" }
            create("pixel6Api35") { device = "Pixel 6"; apiLevel = 35; systemImageSource = "google" }
        }
    }
}
```

Reports: `app/build/reports/androidTests/connected/index.html` (managed devices: `.../androidTests/managedDevice/`).

### CI

`.github/workflows/build.yml` has an `instrumented` job: on pull requests it runs `./gradlew connectedDebugAndroidTest`
on API 24 and API 35 emulators with `reactivecircus/android-emulator-runner@v2`. It is advisory
(`continue-on-error: true`), so an emulator hiccup cannot block a merge; read its artifact
`instrumented-reports-apiNN`.

## 3. Not covered

* **Screenshot tests are not implemented.** The previews (`S01_...` to `S77_...`, light and dark) are the natural
  inputs. To add them later:
  * Roborazzi (JVM, Robolectric): add the `io.github.takahirom.roborazzi` plugin, `roborazzi`,
    `roborazzi-compose` and `robolectric` as `testImplementation`, enable
    `testOptions.unitTests.isIncludeAndroidResources = true`, then write tests that call the stateless screens inside
    `AppTheme(dark = ...)` and `captureRoboImage()`. `./gradlew recordRoborazziDebug` writes the baselines under
    `app/src/test/screenshots`, `./gradlew verifyRoborazziDebug` compares them in CI. The unit tests run on JUnit 5, so
    these tests need the JUnit Vintage engine (or a separate source set) because Robolectric is JUnit 4.
  * Paparazzi (JVM, layoutlib, no Robolectric): add `app.cash.paparazzi`, render each preview with
    `paparazzi.snapshot { ... }`; `./gradlew recordPaparazziDebug` and `verifyPaparazziDebug`. It cannot render some
    Android-only views (AndroidView, camera), which the stateless screens avoid.
* **Monkey run (30 minutes without crashes or ANRs, PRD section 11)** is manual, on a debug build:

  ```
  adb shell monkey -p com.qrcode.scanner.barcodereader.generator.scan.qrcode.createqrcode.debug --throttle 100 -v 100000
  ```

  Grant the camera permission first
  (`adb shell pm grant com.qrcode.scanner.barcodereader.generator.scan.qrcode.createqrcode.debug android.permission.CAMERA`)
  and watch `adb logcat -b crash` and `adb shell dumpsys activity processes` for ANRs.
* The live camera pipeline (CameraX, ML Kit decoding of real codes, torch, zoom), scanning a picked image through the
  Photo Picker, saving to the gallery and the SAF export need a device and a human; only their ViewModels and pure
  logic are tested.
* Wi-Fi connection (`WifiNetworkSpecifier` / suggestions), Play In-App Review and Updates, UMP consent and real ads.
* Accessibility audits (TalkBack, font scale 200 percent, contrast) and the R8 release build are checked by hand and by
  `assembleRelease` in CI, not by tests.

## 4. Coverage

The target (PRD section 11) is at least 80 percent line coverage on parsers, safety checker, validators and use cases,
which are plain JVM code. JaCoCo is not wired into the build on purpose (it instruments debug builds and slows
every CI run). To measure it locally, add to `app/build.gradle.kts`:

```kotlin
plugins { jacoco }

android.buildTypes.getByName("debug").enableUnitTestCoverage = true   // android-test: enableAndroidTestCoverage = true

tasks.register<JacocoReport>("jacocoUnitTestReport") {
    dependsOn("testDebugUnitTest")
    reports { html.required.set(true); xml.required.set(true) }
    val excludes = listOf("**/R.class", "**/R$*.class", "**/BuildConfig.*", "**/*_Factory*", "**/*_HiltModules*", "**/Hilt_*", "**/*Directions*")
    classDirectories.setFrom(
        fileTree("$buildDir/tmp/kotlin-classes/debug") { exclude(excludes) },
    )
    sourceDirectories.setFrom("src/main/java")
    executionData.setFrom(fileTree(buildDir) { include("jacoco/testDebugUnitTest.exec") })
}
```

then `./gradlew jacocoUnitTestReport` (report in `app/build/reports/jacoco/jacocoUnitTestReport/html`). The instrumented
coverage report comes from `./gradlew createDebugAndroidTestCoverageReport`. Kover is an alternative with less
configuration if the project wants a coverage gate in CI.
